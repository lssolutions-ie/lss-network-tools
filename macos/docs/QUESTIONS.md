# Questions for the project owner — macOS GUI

Decisions that are genuinely yours. In each case the most conservative choice was taken so work could continue; change it later if you disagree.

## Before M1

- **Bugs found in the bash tool during research — fixed on this branch, not on `main`.** Five pre-existing CLI issues surfaced while mapping the script: (1) Build A Report's export directory is ignored since v1.2.246 because the report-name guard was inverted (a regression from the review fixes); (2) `build_report_for_run_dir` rewrote the manifest only when it was missing, so rebuilt PDFs could miss tasks; (3) stress-test JSON files were written 0600 root-only (mktemp + mv), unreadable by a GUI running as the user; (4) Task 10's skipped / early-failure results went to a non-indexed `gateway-stress-test.json` that the report, manifest and findings code never saw; (5) Task 20 returned 0 on insufficient privileges while Task 18 returns 1. They are committed here as **v1.2.247 (M0)** and will reach `main` with the GUI PR, because you asked for `main` to stay untouched until the merge. If you want CLI users to get them sooner, cherry-pick the single M0 commit onto `main` and release it; nothing in it depends on the GUI.
- **Metal Toolchain download.** Building SwiftTerm needs the Xcode Metal toolchain component, which was not installed on this Mac. It was downloaded (user-level, ~minutes, no sudo). Alternative would have been pinning SwiftTerm below v1.15 (older, unmaintained). Documented in DECISIONS.md and the build script.

## M1

- **Screen Recording permission for pixel-exact screenshots.** `screencapture -l` and `CGWindowListCreateImage` both refuse to image the app's window because the terminal running the build scripts has no Screen Recording permission. Evidence is produced by the app rendering itself instead (`--screenshot` / `--render-detail`), which is faithful except that `cacheDisplay` draws a scrolled sidebar unclipped. If you want exact window captures, grant Screen Recording to your terminal app (System Settings → Privacy & Security → Screen & System Audio Recording); `scripts/screenshot.sh` will then use the window-server path automatically.
- **Build directory outside the repo.** Products go to `~/Library/Caches/ie.lssolutions.lss-network-tools/build` because `~/Documents` is iCloud-synced and its xattrs break `codesign`. Set `LSS_GUI_BUILD_DIR` if you prefer another location (e.g. a non-synced volume), or move the checkout out of `~/Documents` and the default could return to `macos/.build`.
- **Terminal colours.** The pane follows SwiftTerm's defaults (black background after the CLI starts, which suits the CLI's yellow/cyan palette). Say so if you want a light theme matching Terminal.app's "Basic" profile.

## M2

- **Anonymised fixtures from real client runs are in the repository** (`macos/Tests/Fixtures/runs/`, six directories) — and the repository is public. Client, site, note, preparer, hostnames, SSIDs, domains and public addresses are replaced; private IP plans, vendor strings, MAC OUIs, open ports, timings, warnings and findings are the originals. Two things changed during the M5 review: (1) a DHCP `TFTP Server Name:` option had slipped through the first anonymiser (one real server hostname and domain); the rule now hashes every host-name-looking token in free text, the fixtures were regenerated, and the local commits were rewritten so the value never reaches GitHub; (2) the hashing salt is now **private** (`~/.config/lss-network-tools/fixture-salt.hex` on your Mac) because a public salt let anyone confirm a guessed client or site name against the slugs. If you consider the remaining content sensitive, delete the six directories and keep `synthetic/` + `synthetic-run/`; the run-scanning tests pin the count of six and would need adjusting.
- **Hand-written stress-test results.** No real run has a readable Task 10 or 14 result (older CLI versions wrote them 0600 root), so the full-run fixture's stress results are invented numbers in the engine's shape. The views for tasks 10 and 13–20 are therefore verified against synthetic data only; the first real run through the GUI (M3) should be compared against them.
- **Which runs the GUI browses.** The browser reads the installed CLI's `output/` under `/usr/local/share/lss-network-tools` (from `install.env`). Runs made with a portable copy of the script elsewhere are not listed; say so if you want a configurable extra directory in Settings.

## M3

- **No root run was possible in this session.** `sudo` needs a password here, so the non-interactive mode was verified unprivileged (`--run-task list`, exit codes 2/4/5, the interactive regression diff) and the `@@LSS` fixture streams under `macos/Tests/Fixtures/progress/` are hand-written to the contract. Please run one task from the app, or `sudo lss-network-tools --run-task 1 --interface en0 --client Test --location Lab 2>progress.log`, and compare `progress.log` with the fixtures; the parser is tolerant of extra fields, but event and field names must match.
- **One sudo password per run until M4.** sudo's timestamp is per tty and every run is a new pty, so the terminal asks for the password at the start of each run (and of each Rebuild Report). The privileged helper in M4 removes the prompt entirely on a root-owned tool chain; with user-owned Homebrew it is the macOS administrator dialog at the chosen cadence instead (GUI 1.0.1).
- **`--preserve-env=LSS_SSH_PASSWORD` relies on the default macOS sudoers rule** (`%admin ALL=(ALL) ALL`, which lets administrators preserve named variables). A locked-down sudoers would make Task 19 from the GUI fail with a sudo error; the CLI path is unaffected.
- **The interactive CLI no longer auto-starts** when the app opens (the M1 behaviour). It is one click away: the Run Audit screen's "Open Interactive CLI Session" button or the Terminal menu. Say so if you would rather have the M1 behaviour back as a setting.

## M4

- **A Developer ID is needed for everything distribution-related.** This Mac has no code-signing identity, so the app, helper and Sparkle framework are ad-hoc signed: SMAppService registration and Team-ID-based XPC validation could only be exercised as far as macOS allows for ad-hoc bundles (outcome recorded below once attempted), notarisation and a keyed Sparkle feed were verified only in their "skipped cleanly" form, and the DMG is unsigned. With `CODESIGN_IDENTITY`, `CODESIGN_TEAM_ID`, `NOTARY_KEYCHAIN_PROFILE` and a Sparkle key pair (`generate_keys`) set, `make build dmg notarize appcast` is the full release path; the first signed build should re-run the helper registration and one update cycle. — **Closed 2026-10-04 (owner decision, GUI 1.0.1):** the app is a personal tool, never sold or distributed; **no Developer ID, ever**. Ad-hoc signing is permanent, notarisation and Sparkle keys will not happen (the code stays and skips cleanly). The consequences are designed in: `make install` re-registers the helper on every install because an ad-hoc cdhash changes with each build, Gatekeeper is not involved for a locally built app, and the permissions are granted by hand from the Setup & Permissions window ("during install just ask for all permissions manually and I will de-restrict them in Settings").
- **Sparkle feed location.** The feed is the committed `macos/appcast.xml` served raw from the `main` branch. That means a GUI release is two steps: publish the `macos-vX.Y.Z` release with the DMG, then commit the regenerated appcast. If you prefer a single step, host the appcast as a release asset of a fixed "macos-latest" release instead; the URL is one line in `Resources/Info.plist.in`. — **Closed 2026-10-04:** no Sparkle keys will exist (personal tool), so the feed is never used; the file and the script stay as they are.
- **Location permission for the app.** Wireless surveys from the app scan with CoreWLAN under the app's own Location permission (bundle id `ie.lssolutions.lss-network-tools`), so the Mac gets a second Location entry next to the CLI's `LSS-WiFiScan.app`; the CLI's `--uninstall` resets only its own. Ad-hoc signatures change with every build, which can make macOS ask again after a rebuild — a Developer ID signature is stable. — **2026-10-04:** accepted as the permanent state (no Developer ID); the Setup & Permissions window has a Location Services row with Request / Open Location Settings so re-granting after a rebuild is one click.
- **Helper fallback default.** Until the helper has been verified with a signed build, the app's privilege mode defaults to the pty + sudo path; the helper is opt-in from Settings → Privileges.
- **Helper registration outcome on this Mac (ad-hoc build).** `SMAppService.register()` threw "Operation not permitted (SMAppServiceErrorDomain 1)" yet recorded the daemon: status went from `notFound` to `requiresApproval`, `sfltool dumpbtm` lists "LSSHelper, Type: daemon, Disposition: [enabled, disallowed, not notified]", and `launchctl print system/…helper` does not know the service yet. It is waiting for an administrator to approve it under System Settings → General → Login Items & Extensions; after approval, Settings → Privileges → "Check Again" should report its version and the first helper run can be tried (the registered copy is the agent's scratch build under `~/Library/Caches/ie.lssolutions.lss-network-tools/build-helper/app/` — unregister it from that copy or approve it, then register the real build). No end-to-end helper run has happened yet. — **2026-10-04:** `make install` now does exactly this on every install (unregister from the old `/Applications` copy and the build-dir copy, register from the installed copy, open Login Items through the Setup window). Copies older than the `--unregister-helper` flag are skipped by the installer (their automation would open the GUI instead), so a registration left by such a copy — the scratch build under `build-helper/`, or the 1.0.1 build installed before this change — is simply replaced by the new copy's; if the helper then shows "enabled" but does not answer, press Re-register in the Setup window.
- **The installed CLI is v1.2.245.** The app's runs need v1.2.249 (`--run-task`). Since the M5 review the app probes `--run-task list` on every refresh and disables New Run / Continue / Rebuild with the message "The installed command-line tool (v1.2.245) does not support non-interactive runs. Update it with `sudo ./install.sh` from the repository, then Settings → Re-detect." — nothing fails after a password any more. The run browser works with the old install. The final screenshots were taken with the developer override pointing at this branch's checkout.
- **iCloud Drive and the checkout.** The repository lives in `~/Documents`, which iCloud syncs: it created hundreds of "name 2.ext" conflict copies during the fast rewrites of this work (guarded now by `lint.sh`, `build-app.sh` and `.gitignore`), and a syncing fixture tree stalled the run browser's directory watcher (now opened off the main thread) and `RunLoader`. Moving the checkout (or at least the worktree) out of iCloud Drive would remove both hazards.
- **Homebrew-first PATH as root.** The helper (like the CLI's own wrapper and `sudo lss-network-tools` today) runs the script with `/opt/homebrew/bin` first in PATH, so `python3`, `nmap`, `jq`… from the user-owned Homebrew prefix execute as root. This is the CLI's existing trust model (it needs Homebrew's python3 for the PDF); the helper only removes the password prompt. If you want to close it, pin the interpreter paths in the wrapper or require root-owned tool locations. — **Superseded 2026-10-04 (GUI 1.0.1):** a user-owned prefix now requires administrator authentication before the helper runs it (contract §11.2), so the helper no longer removes the prompt for it; pinning the paths or making the tool chain root-owned would make runs password-free again.
- **`--output` outside the run directory — resolved in the M5 review.** The validator now accepts `--output` only when it names a run directory; the caller-owned branch (root following a planted symlink) is gone. If you want exports from the app later, copy the finished 0644 report out of the run directory as the user — no root needed.
- **The helper serves administrators only and declines user-owned tool chains (M5 review) — resolved 2026-10-04 (GUI 1.0.1).** Two rules were added after the review: the XPC connection must come from a member of the `admin` group (sudo's own rule), and the helper refuses to run as root when any directory the engine searches for its tools (`/opt/homebrew/bin`, `/usr/local/bin`, …) or any tool it needs (`nmap`, `jq`, `python3`, `tcpdump`, `speedtest-cli`) is writable by a non-root user. On this Mac Homebrew is user-owned, so the helper declined every run. **Decision:** keep the rule for password-less runs, but let the helper run a user-owned tool chain after the user authenticates as an administrator through the standard macOS authentication dialog (Authorization Services; Touch ID where macOS offers it) — the same boundary `sudo` draws, since `sudo lss-network-tools` already runs those binaries as root after a password. Root-owned tool chains stay password-free; how often the dialog appears is Settings → Privileges → "Ask for authentication". The admin rule is unchanged. Details: contract 07 §11.2, DECISIONS.md.
- **Progress events are now authenticated per run** (`LSS_PROGRESS_TOKEN`). CLI users are unaffected; only the app sets the token.
- **Location permission is asked again after every ad-hoc rebuild** (locationd authorises "without a requirement string"). Expected until the app is signed with a stable identity. — **Closed 2026-10-04:** permanent (no Developer ID); the Setup window's Location row re-requests it.
- **Sparkle feed returns 404 until merge.** A keyed build checking for updates before `macos/appcast.xml` exists on `main` shows Sparkle's error alert; this resolves itself with the merge. — **Closed 2026-10-04:** moot, no keyed build will be made (personal tool).

## GUI 1.0.1 (install + setup, 2026-10-04)

- **Login Items approval after every `make install`.** Because the helper is re-registered from a new cdhash each time, macOS may ask you to allow "LSS Network Tools" under *Allow in the Background* again; the Setup window opens that pane. If that gets tiresome, the alternatives are a stable signing identity (ruled out) or keeping the `sudo` route for runs (Settings → Privileges → Run tasks with), which needs no helper at all.
- **Local Network permission and root processes.** The Setup window requests the Local Network permission for the app itself (a 3-second Bonjour browse — macOS offers no API to read or request this permission directly). Whether the scans, which run as root through `sudo` on a pty or through the LaunchDaemon, are subject to the app's Local Network grant at all could not be verified on this Mac; if a run finds no hosts from the app while the same command works in Terminal, allow the app under Privacy & Security → Local Network and say so.
- **The installed CLI must be v1.2.250 for the menu item.** `make install` compares the installed `lss-network-tools --version` with the checkout and prints `sudo ./install.sh` when it is older; it never runs it (the only root step of the install is yours).

## GUI 1.0.1 (authorization gate)

- **Touch ID in the authentication dialog depends on SecurityAgent.** The helper's rights are plain `authenticate-user` admin rules; whether the dialog offers Touch ID (rather than only a password field) is decided by macOS for that rule class and Mac model, not by the app. This Mac could not confirm it — please verify on a Touch ID Mac that the dialog shown before a helper run with a user-owned tool chain accepts Touch ID; if it does not, the password still works and nothing else changes.
- **Should "once per app session" stay?** The cadence picker ships three choices: every run, every five minutes (default, matching sudo), and once per app session (asks at the first run, then not again until you quit or press "Lock now"; the right's timeout is effectively unlimited, the credential dies with the app's AuthorizationRef). The last one is the most convenient and the least sudo-like: for it the helper enforces no time bound of its own — the request names the session right and the credential lives as long as the app process (contract §11.2 S2/S3). It is shipped because the default is five minutes and the rule is `shared = false` (no other app can reuse the credential); say so if you would rather drop it.
- **First helper-route run with 1.0.1.** No end-to-end helper run has happened on this Mac yet. After registering 1.0.1 and approving it, run one task through the helper on this user-owned Homebrew install and check the unified log (`log show --predicate 'subsystem == "ie.lssolutions.lss-network-tools.helper"' --last 10m`) for the notice `run for uid … authorised by an administrator credential for right …`; also try Cancel while the dialog is up (the run should end as cancelled and Settings should show "Not authenticated" afterwards).
